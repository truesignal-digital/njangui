Ship from Trunk

One branch, many destinations — the deployment model behind njangi, Bluesky, and most modern teams, and how it maps to classic SRE ideas.

1The one idea everything hangs on

Environments are destinations, not branches.

There is exactly one long-lived branch: main (the "trunk"). Staging and production are not branches you merge into — they are places the same code gets delivered to, in order, with gates in between.

 feature branch ──PR──▶ main ──▶ [tests] ──▶ staging ──▶ prod
                          │
                          └── the only branch that lives longer than a PR

Everything else in this document is a consequence of that idea.

2The alternative, and why it lost

The older model (GitFlow and friends) gives each environment its own branch: develop → staging → master. Promotion means merging branch into branch.

Branch-per-environmentTrunk + destinations
"What's on prod?"Whatever the master branch has drifted toA specific commit of main
Hotfix pathFix on master, then back-merge to staging and develop — three merges, easy to miss oneFix on main, flows outward automatically
Failure modeDrift: branches diverge, cherry-picks pile up, "works on staging" stops meaning anythingA bad commit — visible, revertable, one place
Who it fitsSlow release trains (quarterly firmware, regulated release cycles)Continuous delivery — almost everyone else

The deep problem with branch-per-environment: it stores deployment state in version control. Git is good at recording history, bad at being a dashboard. Trunk-based flips it: git records history, the pipeline records what is deployed where.

3Deploy ≠ Release

The most useful distinction in all of release engineering:

Deploy
code is running on servers / sitting on the update CDN
Release
users actually experience it

They can be separated — and separating them is what gives you control. A backend can deploy ten times a day while users' apps change only when you deliberately publish a bundle to their channel. The "release moment" becomes a small, cheap, reversible decision instead of a big scary event.

In njangi this shows up as three artifact types, each with its own release mechanics and its own speed:

ArtifactDeployed byReleased whenSpeed
Convex functionsmerge to main (auto: staging, then prod)immediately — server truthminutes
JS bundle (OTA)eas update --channel …you publish to that channelhours
Native binaryeas build + store reviewstore approves + user updatesdays
Knowing the speed tier of a fix before you write it changes where you put the code. Money math lives in convex/lib partly because that's the minutes tier.

4Channels: promotion without branches

A channel is a named audience. Each installed build listens to exactly one channel; publishing a JS bundle to a channel releases it to that audience and no other.

                        ┌── channel: development ──▶ your simulator / dev client
 main ──▶ JS bundle ────┼── channel: preview     ──▶ staging testers
                        └── channel: production  ──▶ real users

Promotion = publishing the same commit to the next channel. No merge, no rebuild of source, no drift. Bluesky runs exactly this: every merge auto-publishes to their testflight channel (their rolling staging audience), and a human manually dispatches the publish to production.

This is the mobile version of a classic SRE principle:

Build once, promote the artifact. Never rebuild between environments — a rebuild is a new, untested artifact wearing the old one's name badge.

5Mapping to classic SRE concepts

Environments (dev / staging / prod)

Same names, same purpose as in server-land. The mobile twist: the client build bakes in which backend it talks to, so an "environment" is really a matched pair — (staging backend + staging-channel build), (prod backend + production-channel build). Mixing tiers across the pair is the classic self-inflicted outage.

Blue-green deployment

Server world: run two identical prod environments, cut traffic over atomically, cut back to roll back. Convex gives you the spirit of this for free — a deploy replaces all functions atomically; there is no half-deployed state. What it doesn't give you is instant traffic-shifting rollback: you roll back by redeploying the previous commit (still minutes).

Canary release

Server world: send 1% of traffic to the new version, watch, ramp up. Mobile equivalent: staged OTA rollout — publish an update at 10%, watch Sentry, ramp to 100%. Note njangi's deliberate exception: critical money fixes ship at 100% immediately, because a canary of a ledger fix means 90% of users keep the bug on purpose.

Feature flags

Flags decouple release from deploy within one artifact: code ships dark, a flag turns it on per-user/per-percent. They compose with channels — channels choose which bundle an audience gets, flags choose which code paths run inside it. Cost: every flag doubles the states you must test. Rule of thumb for a small team: use channels until a change genuinely needs per-user gradual exposure, then reach for a flag — and delete it after.

Rollback & MTTR

Every tier needs a rollback story before you need it:

TierRollbackCost
Convexredeploy previous commitminutes
OTArepublish previous update to the channelminutes–hours
Native binarythere isn't one — store review againdays

That bottom row is why the additive evolution rule exists (never break a public function signature or persisted shape in one step): the one artifact you cannot recall is the one installed on someone's phone. The server must stay compatible with every binary still in the wild.

Gates vs approvals

A gate is automated (tests must pass, staging deploy must succeed). An approval is a human saying "go". Mature pipelines are gates almost everywhere with one deliberate human step at the point of highest blast radius. In njangi today that human step is publishing OTA to the production channel. When real users arrive, a second one appears in front of the prod backend deploy (the "promotion flip").

DORA metrics — how you'd measure this machine

The research finding worth internalizing: speed and safety are not a trade-off. The four metrics improve together, because small frequent changes are easier to test, review, and undo than big rare ones.

6Common traps

Staging drift. Staging config quietly diverges from prod (different env vars, stale schema, missing webhook) and green-on-staging stops predicting green-on-prod. Defense: staging deploys the same commit automatically — only credentials and data may differ.
The forgotten promotion. Every manual step in a pipeline is a step someone will skip on a Friday. Each human approval must be one obvious action with an obvious owner — or it should be a gate instead.
Rebuilding between environments. "It's the same code" — it isn't; it's a new build with new dependency resolution. Promote artifacts (or redeploy the exact commit), never re-create them.
Version state in git. Release branches, version-bump commits, environment branches — all store pipeline state in version control. Let git hold history; let the pipeline (channels, deployments, dashboards) hold "what is where".

8Control on a trunk: "what if I don't want it in prod?"

Auto-deploy sounds like losing control. It's actually relocating control: on a trunk, the merge is the release decision for the backend. Three mechanisms replace the old "hold it on a branch" habit:

1 · Don't merge it

The PR is the holding area. CI, review, and your own judgment run before the code can reach any environment. If something isn't ready for prod, it isn't ready for main — that sentence is the whole model. Corollary: PRs stay small, because a small PR is a small release decision.

2 · Ship it dark

Merge code that runs nowhere: a new Convex function nothing calls yet, a screen no navigation reaches, a component behind a flag that's off. The code deploys — dark — and integration pain surfaces early while users see nothing. This is how large features land on trunk in twenty small PRs instead of one six-week branch that no longer merges. (Long-lived feature branches are just hidden inventory; dark shipping is inventory you can see and test.)

3 · Revert first, investigate second

When something bad does land: git revert the merge commit, merge the revert, and the pipeline un-ships it in the same ~3 minutes it shipped. Revert is not an admission of failure — it's the cheapest MTTR move that exists. Debug on your own time, on a branch, with prod already healthy. Roll forward (fix instead of revert) only when the revert itself is riskier — e.g. a migration already ran.

Notice what these three have in common: none of them involve a staging branch, a release manager, or asking permission. Control lives in small merges, dark code, and fast reverts — not in process ceremony.

9Knowing what is where

A pipeline you can't interrogate breeds fear, and fear breeds ceremony. The antidote is a release manifest: one command that answers "what exactly is in prod?" from the pipeline's own sources of truth — never from memory or local state.

bun run release:status
main            eaf3fb5  feat(ci): staging Convex deploy gates prod
backend prod    2b32f97  success  2026-07-04 06:12Z
ota production  nothing published yet
ota preview     runtime e19b3fc  "fix: retry sso username collisions"
build           IOS     preview  FINISHED  eaf3fb5
build           ANDROID preview  FINISHED  eaf3fb5

Each line has exactly one source of truth:

QuestionSource of truth
What commit is prod's backend?last green Deploy Convex run on main
What JS do users run?last update published to the production channel
What binaries exist?EAS build list (per profile, per platform)
Is anything broken right now?Sentry — the pipeline's feedback loop, not part of the pipeline itself

SRE framing: this is observability of the delivery system itself. The same discipline you apply to the app (server truth over optimism) applies to the pipeline — never trust a human's memory of what was deployed when a machine records it.

10The release ritual

Merging is automatic delivery to staging. Releasing to users is a ritual — four steps, always the same, so that "did I mean to do this?" is never in doubt:

# 1 · stand on exactly what you intend to ship
git checkout main && git pull

# 2 · know the gap — read the commits that would go out
bun run release:status
git log --oneline <last-released-commit>..main

# 3 · the choosing — this command IS the release
npx eas-cli@latest update --channel production --environment production \
  --message "what this release is, in one line"

# 4 · confirm reality changed the way you meant
bun run release:status

Three details carry the weight:

--environmentbakes that environment's EXPO_PUBLIC_* values into the bundle. Publishing a prod-channel update with staging env vars is the cross-tier mixing from §5 — the flag is not optional.
--messageyour release note to future-you. It appears in release:status and the dashboard forever; write it like you'll be reading it during an incident, because you will.
runtime matchan OTA only applies to builds whose fingerprint matches. If anything native changed since the last build, the update silently reaches nobody — the mismatch in release:status is the tell, and the answer is a new build, not a louder publish.

Same ritual, lower stakes: replace production with preview to release to staging testers. Practice the muscle where mistakes are free.
