# Shipping pipeline — CI/CD, releases, telemetry

Repo: `github.com/truesignal-digital/njangui`. Stack: Expo SDK 56 / RN 0.85, Convex, Clerk, bun 1.3.6, 2 devs.

The single most important architectural fact for this pipeline: **ledger math ships at Convex-deploy speed (minutes), client JS ships at OTA speed (hours), native code ships at store speed (days)**. Every "where does this code live" decision is also a "how fast can we fix it" decision — the CLAUDE.md rule that money math never lives in components is load-bearing for operations, not just correctness.

Phases are adoption-gated per the house rules (strangler, no scale machinery without the symptom).

---

## Phase 0 — landed with this doc: PR quality gate

`.github/workflows/ci.yml`: matrix over the three existing gates (`typecheck`, `lint:design`, `bun run test` = money-math suite, 97 tests / ~0.5s), aggregated into one stable required check named **`CI`** (summary job with `if: always()` + `test "$RESULT" = "success"` so a skipped/cancelled leg can never pass silently).

Repo changes that made CI work in a clean checkout:

- `expo-env.d.ts` committed (removed from `.gitignore`). Without it, `tsc --noEmit` fails in a fresh clone (`TS2882` on the `../global.css` side-effect import) because the file is only generated by the dev server.
- `"test": "bun test convex/lib"` script added. Note the bun footgun: bare `bun test` bypasses package.json scripts and globs the whole repo — always `bun run test`.

**Known gap:** `.expo/types/router.d.ts` (typed routes) is not generated headlessly, so CI typechecks `Href`s looser than local dev. Mitigation is the existing CLAUDE.md rule: object-form navigation only, never cast. Revisit when Expo ships a headless router-types command.

Deliberately NOT in CI:

- `expo-doctor` — network-dependent, advisory, flaky. Stays a local `bun run doctor`.
- ESLint/Prettier — don't exist in this repo. `scripts/lint-design-system.ts` IS the linter.
- Convex codegen drift check — `bunx convex codegen` requires a configured `CONVEX_DEPLOYMENT` and a network round-trip; it cannot run as an offline PR check. Drift is caught by the typecheck job (against committed `convex/_generated`) and by `convex deploy`'s own codegen+typecheck at deploy time.

### Branch protection (manual, GitHub → Settings → Branches → `main`)

- [ ] Require a pull request before merging (0 required approvals is fine at 2 devs — the gate is CI, not review theater)
- [ ] Require status checks: exactly one, **`CI`**
- [ ] "Require branches to be up to date": off (not worth the churn at 2 devs; the deploy workflow re-runs tests at the merged commit to cover the two-green-PRs-merge-broken case)
- [ ] Do not exempt admins — it's a money app

## Phase 1 — before real testers: Convex prod deploy, EAS linkage, Sentry

### 1.1 Convex prod deploy (workflow already committed, dormant)

`.github/workflows/deploy-convex.yml` deploys prod on push to `main` touching `convex/**`, `package.json`, `bun.lock`, or `convex.json` (dep bumps ship with the deploy, not silently later). It re-runs `bun run test` + `bun run typecheck` at the merged commit **before** `bunx convex deploy` — `convex deploy` typechecks but never runs the money-math suite, and two individually-green PRs can merge broken.

The job is gated on repo variable `CONVEX_DEPLOY_ENABLED == 'true'` so it no-ops until secrets exist.

Activation checklist:

- [ ] Create prod deployment in the Convex dashboard; generate a **production deploy key** → GitHub secret `CONVEX_DEPLOY_KEY`
- [ ] Set repo variable `CONVEX_DEPLOY_ENABLED=true`
- [ ] Set prod server env vars in the Convex dashboard: `CLERK_JWT_ISSUER_DOMAIN`, `CLERK_WEBHOOK_SECRET`, `CLERK_SECRET_KEY`, `RESEND_API_KEY`
- [ ] Safety: `DEV_SEED_ENABLED` unset (the WhatsApp-OTP system and its `DEV_OTP_PROVIDER`/`TWILIO_*` env vars were removed 2026-07).

**Preview deploys per PR: skipped.** They are a Convex **Pro** feature, and the mobile client would need `EXPO_PUBLIC_CONVEX_URL` repointed per preview — awkward on device builds. Adopt when a backend PR is risky enough to need exercising from a real client pre-merge AND the team is on Pro.

### 1.2 Client compatibility rule (new house rule — the flip side of deploy speed)

Once un-forceable binaries exist (phase 2), a 1-minute Convex deploy is also a 1-minute way to break every old client. **Public Convex function signatures and returned shapes evolve additively while any released binary depends on them**: new args optional, never rename/retype/remove args or `returns` fields in one step — deprecate, ship clients, then remove. This mirrors the existing "evolve persisted shapes additively" storage rule. Candidate lint (phase 3): flag removed/renamed exported convex functions in a diff.

### 1.3 EAS linkage

- [ ] `eas init` (writes `owner` + `extra.eas.projectId` into app.json — currently missing; also unblocks push-notification testing per docs/build-plan.md). Commit the app.json change.
- [ ] EAS environment variables per environment (`development`/`preview`/`production` — eas.json profiles already declare `environment:`): `EXPO_PUBLIC_CONVEX_URL`, `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY`
- [ ] Connect the GitHub repo in the Expo dashboard (prerequisite for EAS Workflows in phase 2)

Build cadence (fits the free tier — 15 iOS + 15 Android builds/month, ~100 workflow minutes):

| Build | Trigger | Cadence |
| --- | --- | --- |
| `development` / `development-simulator` | Manual (`bun run eas:build:development:*`) | Only when native deps change |
| `preview` (Android APK, internal) | Manual `bun run eas:build:preview:android` | Weekly-ish for testers |
| `production` | EAS Workflow on release tag (phase 2) | Per store release |

**Never build on PR/push** — burns the free tier for nothing, especially with `ios.buildReactNativeFromSource: true` making iOS builds long (revisit whether that flag is still needed; it disproportionately eats build minutes). Division of labor: **GitHub Actions for cheap checks + Convex deploys; EAS Workflows for builds/submit/OTA/E2E.**

### 1.4 Sentry

The repo staged for this: `src/lib/logger.ts` prod transport is a documented no-op seam.

1. Install: `bunx expo install @sentry/react-native` (NOT `sentry-expo` — deprecated since SDK 50), then `npx @sentry/wizard@latest -i reactNative`. The wizard assumes npm — delete any stray `package-lock.json` it leaves in this bun-only repo.
2. app.json plugin: `["@sentry/react-native/expo", { "organization": "<org>", "project": "njangi" }]`
3. `Sentry.init`: `sampleRate: 1.0` (low volume; every error in a money app matters), enable sessions (release health — crash-free rate per release is the one number to watch weekly). Once OTA lands, tag `updateId`/`channel`/`runtimeVersion`.
4. **Wire as a transport inside `src/lib/logger.ts`, never at call sites** (exactly what the seam was left for):
   - every log → `Sentry.addBreadcrumb`; only `logger.error` → Sentry event (`captureException` for Error objects, `captureMessage` for strings)
   - apply `isNetworkError` in the transport, checking the metadata `error` key as well as message strings (verify Convex client disconnect strings match the classifier)
   - no app-state imports in the transport (import-cycle footgun); tests get an empty transport array
   - level contract for CLAUDE.md: `debug` dev-only, `info` breadcrumb, `warn` expected failure, `error` actionable event
5. Source maps: native EAS builds upload automatically **iff** `SENTRY_AUTH_TOKEN` is set as an EAS env var (sensitive visibility, all three environments). OTA updates do NOT auto-upload — see phase 2.
6. Same PR, cheap win: **log ring buffer** — ~20 lines in logger.ts, every log to a module-level 500-entry buffer before level filtering, plus a hidden dev-gated "System Log" screen reachable from Profile. For field money disputes in low-connectivity contexts, "screenshot the system log" beats remote debugging.

Checklist:

- [ ] Sentry org + project
- [ ] `SENTRY_AUTH_TOKEN` as EAS env var (sensitive)
- [ ] Alert rule: every new issue → email (add rate-based rules only when noisy)
- [ ] logger.ts transport + ring buffer PR

## Phase 2 — first store release: OTA + submission

Gate: shipping a binary users can't be forced to update.

### 2.1 expo-updates + EAS Update

Install `expo-updates`; app.json:

```json
"runtimeVersion": { "policy": "fingerprint" },
"updates": { "url": "https://u.expo.dev/<projectId>" }
```

**Fingerprint policy, not appVersion** — it hashes the native dependency graph, so a native-module add structurally cannot serve incompatible JS to old binaries. "Forgot to bump the runtime version" is not an acceptable failure mode for a money app. Three channels in eas.json build profiles (`development`/`preview`/`production`) — no per-PR channels.

Release workflow `.eas/workflows/deploy-production.yml` on release tag, using EAS Workflows' native job types:

```
fingerprint → get-build(profile: production, fingerprint_hash)
  ├─ build exists → update (OTA to production channel) → sourcemap upload
  └─ no build     → build → submit
```

JS-only releases become OTA publishes, native-surface releases become store builds — no human deciding which.

**Money-flow hot-fix lanes:**

- Ledger-**math** bug → server-side, fixed by the phase-1 Convex deploy in minutes. No OTA, no store review. This is the payoff of server-truth — keep resisting money math drifting into the client.
- Client money-**flow** bug (pay screen wiring, confirmation UI, meeting queue):
  - Critical correctness fix → `eas update --channel production` at **100% immediately**. Staging a correctness fix means knowingly leaving users on broken money UI.
  - Risky behavioral change → `--rollout-percentage 10`, watch crash-free rate, `eas update:edit` to widen 10 → 50 → 100 over ~a day.
- **Rollback runbook committed BEFORE the first production OTA** (5 lines in docs/): `eas update:rollback`, or `eas update:republish --destination-channel production` of last-known-good. Devices cache the bad bundle until something newer arrives — rollback is publishing, not deleting.
- After every `eas update`: `npx sentry-expo-upload-sourcemaps dist` — NOT automatic (unlike native builds); chain it in the workflow.
- Apply-side hook (~80 lines, mounts once on Home, `isEnabled && !__DEV__`): silent fetch ~10s after launch; `reloadAsync()` only when returning to foreground after ≥15 min backgrounded; never prompt. Plus one njangi-specific guard: **never reload while a pay-flow or meeting route is mounted** — a reload mid roll-call or mid claim is a trust catastrophe.

**Cost cliff:** EAS Update free tier caps at 1,000 MAU + 100 GiB bandwidth — it arrives exactly when phase 2 succeeds. Budget for the paid tier when testers become users.

### 2.2 Store submission

eas.json submit profiles: iOS via ASC API key (`ascAppId`/`ascApiKeyId`/`ascApiKeyIssuerId`/`.p8`), Android via service-account JSON, `track: internal`. Key files as EAS secrets, never in git (`.gitignore` already blocks `*.p8`/`*.p12`/`*.jks`). Default iOS submit lands in TestFlight internal; promotion to review stays a human click.

Checklist: Apple Developer + ASC API key; Play Console + service account; channels + submit profiles in eas.json; release workflow; rollback runbook; OTA apply hook with pay/meeting guard.

## Product/ops telemetry — no client analytics SDK at MVP

The interesting events already exist server-side with server-truth accuracy no client SDK can match: every money action writes to Convex (`paymentRecords` with `confirmedAt` denormalized, `activityEvents`, `confirmations`). The two metrics that matter:

- **Payment funnel**: expected → recorded → confirmed per round (counts over `paymentRecords` by state)
- **Confirmation latency**: `confirmedAt − createdAt` distribution — this IS the trust metric; a rising p90 means counterparties aren't confirming and disputes are brewing

Implement as one internal Convex query (or a scheduled daily rollup) read from the dashboard function runner. Zero new deps, zero PII leaving Convex.

Skip (Bluesky-scale machinery, per house rules): GrowthBook/statsig feature gates, provider nesting, exposure events, the 1,400-line typed Events catalog. For remote toggles, a Convex-served config doc beats any flag SaaS — the USSD-content OTA override already proves the pattern. Keep one free idea for later: when product analytics land, start with a small typed `Events` map (~15 events, compile-checked names).

If client-side funnel visibility becomes necessary (symptom: can't tell where users abandon the pay flow *before* anything hits the server): a Convex mutation as ingestion endpoint behind a ~100-line queued MetricsClient (flush on 10s/size/background, one retry on foreground). **Hard rule: telemetry-grade delivery is for telemetry only — money events never ride it.** The meeting queue's write-before-fire + server-ack + idempotency-key pattern is the transactional tier and stays separate.

## Alerting — how 2 devs learn it's broken

| Signal | Mechanism | Phase |
| --- | --- | --- |
| Client crash/error | Sentry: every new issue → email; weekly glance at crash-free rate | 1 |
| Backend function failure | Convex dashboard health + function logs (`console.error` in convex/ lands there — already house convention). On Convex Pro: built-in Sentry exception-reporting integration → same inbox as client errors. Until Pro: daily dashboard glance, honestly stated. | 1 |
| CI/deploy failure | GitHub default failure emails. The Convex deploy workflow failing = prod didn't get the fix — treat that email as a pager. | 0/1 |
| OTA gone wrong | Sentry issues tagged `updateId`/`channel` spike → rollback runbook | 2 |

Skip Slack webhooks/PagerDuty until someone misses a failure email that mattered.
